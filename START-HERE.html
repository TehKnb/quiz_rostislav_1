1. Завдання продукту

Квіз для власників малого та середнього бізнесу. Він збирає контекст, оцінює чотири напрями процесів і показує персональний висновок. Цільова дія — номер телефону та згода на зв’язок щодо персонального бізнес-розбору КНБ. Після успішного запису заявки відкриваються повні пояснення та рекомендації.

Основний офер: «Хочете вдвічі більше чистого прибутку? Що у вашому бізнесі має змінитися першим?» Це бажана ціль відвідувача, не розрахований прогноз зростання. Квіз не обчислює втрачені гроші, не гарантує подвоєння прибутку й не використовує зовнішню ШІ-модель для відповідей.

Результат ґрунтується на детермінованих правилах у app/lib/engine.ts. Обов’язково зберегти пояснення про попередній характер рекомендацій і необхідність перевірки показників та внутрішніх процесів на бізнес-розборі.

3. Технології й запуск

Стек із поточного package.json: React 19.2.6, TypeScript 5.9.3, Vinext 1.0.0-beta.5, Vite 8.0.13, Drizzle ORM 0.45.2, Cloudflare Workers/D1, Wrangler 4.92.0. Використовується структура Next App Router; пакет Next 16.3.4 є у залежностях, але запуск виконується через Vinext/Vite, а не стандартний next start.

Вимоги пакета: Node.js >=22.13.0; менеджер пакетів — pnpm 11.25.0. Команді варто взяти актуальний підтримуваний Node, сумісний із цим lockfile, і спочатку відтворити залежності без їх оновлення. Для встановлення потрібен доступ до npm-реєстру. Не використовуйте автоматичне масове оновлення залежностей до звірки поведінки.

З кореня source/, після встановлення Node і pnpm:

pnpm install --frozen-lockfile
node tests/engine.cjs
pnpm exec tsc --noEmit
pnpm build

У чистому експорті немає .sites-runtime/execution-profile.json; readExecutionProfile() обирає режим portable. pnpm dev у цьому режимі запускає Vinext на порту 5173. Остаточну адресу дивіться у консолі.

Після успішного build застосувати міграцію до локальної D1. Спершу переконайтеся, що файл dist/server/wrangler.json створився:

node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_polite_cammi.sql
pnpm start

pnpm start тут означає локальний Wrangler для зібраного Worker, не production-сервер. Ця команда використовує ту саму .wrangler/state. SQL застосовувати один раз до порожньої локальної бази; повторне виконання CREATE TABLE для наявної таблиці дасть помилку. Для щоденної розробки використовуйте pnpm dev, але звірте фактичний шлях persistence у вашому середовищі, якщо форма повідомляє про відсутню таблицю.

Замість старих абсолютних шляхів /workspace/... і /root/.codex/... зі службових описів використовуйте команди вище. Цей архів не включає інструменти публікації ChatGPT. Секретів для логіки квіза не потрібно; для нового production-хостингу знадобляться власні облікові дані хостингу й CRM.

Перевірка передачі: 52 базові сценарії, додаткові перевірки мультивибору й звітів за чотирма напрямами пройшли; tsc --noEmit завершився успішно. Це перевірка коду в наявному середовищі, не підтвердження чистої інсталяції чи нового зовнішнього деплою.

4. Екрани та поведінка

  • Головна. Офер, CTA, схема чотирьох напрямів, три короткі кроки пояснення.
  • Проходження. Одне запитання за раз, прогрес, назад, збереження/вихід, блокування «Далі» без валідної відповіді. Прогрес показує step / 20, де step — індекс від 0.
  • Результат до заявки. Сфера, чотири кільцеві оцінки, головний висновок, перший крок, чотири рекомендаційні картки з продовженням під блюром. Натискання оцінки показує питання й відповіді відповідного напряму.
  • Офер бізнес-розбору. Дві групи вигод: результат після заявки та персональний розбір. Форма телефону й обов’язкова згода.
  • Успішна заявка. Тільки після успіху POST з’являється підтвердження, розгорнуті пояснення, дії, показники, питання на розбір та кнопка завантаження TXT.
  • Повторне проходження. Скидання поточної сесії через підтвердження; раніше записані заявки не видаляються.

Локальний стан: sessionStorage, ключ knb-quiz-v3. Зберігаються profile, step, view, unlocked, report, receipt. Телефон не зберігається в цьому стані. Продовження працює в тій самій вкладці; це не акаунт і не синхронізація між пристроями. Після закриття вкладки не обіцяти гарантованого відновлення.

Сфери: медицина, б’юті, одяг/взуття/аксесуари, магазин/інтернет-магазин, автобізнес, харчування, будівництво, виробництво, інша сфера. Автобізнес має repair, cars, other. Для іншої сфери або авто/other потрібен текст мінімум 2 символи після trim; максимум поля — 100 символів. Універсальні запитання використовують ключ other.

Варіанти команди 0 та 1 вважаються самостійною роботою; 2, 3, 4 — роботою з командою. Змінюються блок організації роботи, окремі нішеві питання, назви й рекомендації. Точні формулювання є в каталозі; його генеровано викликом question() з реального engine, а не написано окремо.

Мультивибір дозволений лише в №3 і №20. Максимум 3; повторне натискання знімає вибір. У №20 варіант з індексом 6 «Нічого з переліченого…» взаємовиключний з іншими. Масиви — goals та impacts; їх перший елемент дублюється в answers[2]/answers[19]. Це вимога валідації. Старий формат з одним індексом у answers підтримується fallback-логікою selected().

Зміна вже обраної сфери або формату роботи очищає оцінювані відповіді 3–18. Зміна формату роботи також очищає останнє питання та impacts. Зміна авто-підгілки очищає питання 3–10. Після зміни відповідей повний результат знову закривається.

6. Формула балів та головний пріоритет

В оцінюваних питаннях індекс відповіді 0 — найкращий стан, 3 — найслабший. Індекс 4 «Не можу оцінити / не застосовується» виключається з оцінки, не прирівнюється до нуля. Контекстні питання 1–3 та 20 не додають балів.

Для кожної групи потрібні щонайменше 2 відомі відповіді з 4:

score = Math.round(sum(3 - answerIndex) / (knownCount * 3) * 100)

Інакше score = null, показуємо тире й недостатність даних. Приклад: відповіді 0, 3, 4, 4 → 50/100; 0, 4, 4, 4 → недостатньо даних. Межі: <40 — потребує уваги; 40–69 — є основа для покращення; >=70 — процеси налагоджені.

Червона дуга кола відображає цей бал зі 100, а не частку пройденого тесту і не відсоток втраченого прибутку. Нуль — лише фон кола; null — тире.

Головний пріоритет — напрям із найменшим доступним балом. За однакових оцінок використовуються обрані цілі, потім особисті наслідки; може повертатися до двох пріоритетів. Точний порядок розв’язання нічиєї — функція priority(); для повної тотожності переносити її без спрощення.

Мапа цілей у групи: [0,1,3,2,2,-1]. Мапа наслідків: [0,1,2,2,3,3,-1]. Групи 0=маркетинг, 1=продажі, 2=організація/команда, 3=аналітика. -1 не задає конкретної групи.

Якщо немає жодної оцінюваної групи — insufficient. Якщо мінімальний пріоритетний бал >=70 — high; висновок пропонує перевірити стійкість процесів до зростання. Важливий нюанс: high стосується лише оцінених напрямів, не означає, що всі чотири мають достатньо даних.

7. Побудова персонального результату

result(profile) повертає scores, priorities, high, insufficient, evidence, strongSide, conflict, recommendations, directions, deepDive, firstStep, title, explanation, goal, impact, sector.

  • evidence — до двох найслабших оцінених відповідей головного напряму.
  • directions — чотири картки: маркетинг, продажі, організація роботи, аналітика. Для кожної — бал, статус, пояснення, до двох предметних кроків, що зафіксувати, як оцінити зміни, що уточнити на розборі. За нестачею даних — заклик зібрати приклади.
  • deepDive — три частини головного висновку: чому почати тут, зв’язок чотирьох напрямів, послідовність дій.
  • recommendations — збережене поле з трьома рекомендаціями. Поточний фінальний інтерфейс рендерить саме чотири directions; не замінювати їх старим масивом recommendations.
  • strongSide — одна найсильніша відповідь, переважно з іншого напряму.
  • conflict — окреме уточнення, коли економіку пропозицій рахують, а загальний прибуток оцінюють приблизно.

Для fashion/shop є окремий висновок про покупки, що губляться в діалогах: він застосовується, коли головний пріоритет — продажі та обидві відповіді на індексах 9 і 10 дорівнюють 2 або 3. Для самостійної роботи застосовуються власні заголовки й поради, а не автоматична рекомендація наймати людей.

Блюр — оформлення, не захист контенту. Тексти й алгоритм доступні клієнту; unlocked зберігається у sessionStorage. Якщо бізнесу потрібне реальне обмеження доступу, частину звіту потрібно перенести на сервер і видавати за авторизованою сесією/одноразовим токеном після запису заявки. У поточному проєкті такого механізму немає.

8. API заявки

POST /api/leads

JSON: id, phone, consent: true, profile. Готовий валідний приклад — examples/lead-request.json; номер синтетичний, не використовувати для реального дзвінка.

Profile містить: answers — рівно 20 цілих індексів; auto — рядок; other — рядок до 100 символів; goals/impacts — необов’язкові масиви для мультивибору з правилами вище.

Сервер перевіряє Origin, якщо він є; порівнює з origin запиту. Обмежує текст тіла 16000 символами. Номер очищає від пробілів, дужок, крапок і дефісів; український 0XXXXXXXXX перетворює на +380…, 380… доповнює плюсом. Дозволяє міжнародний номер: плюс і 10–15 цифр, перша не нуль; відсікає рядки з однієї повторюваної цифри. SMS-підтвердження немає.

id приймається за regex ^[0-9a-f-]{36}$, інакше генерується randomUUID. Повний report сервер обчислює сам із profile; клієнтський готовий звіт не приймається як джерело істини. Запис — insert з onConflictDoNothing().

КодПоточна поведінка
200{id, report}, Cache-Control: no-store
400Некоректний JSON або невідповідність номера/згоди/profile
403Переданий Origin не відповідає адресі API
413Текст тіла довший за 16000 символів
503Помилка збереження або інший виняток; UI пропонує повтор

Нюанс: JSON null потрапляє у загальний catch і дає 503, а не 400. Зараз це частина фактичної поведінки; виправлення бажане під час підготовки production API.

Повтор того самого id не створює новий рядок, проте API повертає звіт із нового надісланого profile, не звіряючи його з раніше записаним. Для надійної ідемпотентності повертати існуючу заявку при повторі id та окремо обробляти конфлікт різних даних. Особливо перевірити зміну авто-підгілки після вже надісланої заявки: цей шлях не очищає ref id так само, як звичайний вибір відповіді.

GET /api/leads

Потрібен заголовок oai-authenticated-user-id, який на Sites встановлюється платформою. Без нього — 401. Відповідь {rows}: до 200 останніх записів лише з viewer, рівним поточному користувачу, сортування createdAt DESC; помилка бази — 503.

Це не адмінський список усіх лідів. Анонімні заявки мають viewer=null і не потрапляють у звичайний GET поточного користувача. Для команди продажів потрібна окрема серверна роль та захищений список/експорт або передача в CRM.

10. Перенесення на власний хостинг

Варіант 1: залишити Vinext + Cloudflare Workers/D1

Найменше переписування бізнес-логіки. Команда створює власні Worker, D1, домен і конфігурацію деплою. В vite.config.ts використано локальний placeholder database_id; це не реквізити production-бази. Замінити на конфігурацію своєї D1. Не використовувати ідентифікатор Sites як ідентифікатор Cloudflare-ресурсу.

Переглянути залежності від Sites: .openai/hosting.json, sites-vite-plugin, connectorPreview, worker/index.ts, lib/connector-* та app/chatgpt-auth.ts. Квіз не викликає зовнішніх app-конекторів, але стартова інфраструктура їх містить. Для окремого деплою прибрати або адаптувати ці обв’язки, залишивши обробник Vinext, Cloudflare-плагін, UI, engine та D1. sites({mockAuth: ...}) застосовує тестову ідентичність у локальній розробці; це не готова production-авторизація.

Команда повинна налаштувати власну схему авторизації для адміністратора, перевірити міграції на staging, потім налаштувати домен, HTTPS і production-змінні. Команда деплою залежить від обраної конфігурації; архів не містить облікових даних для нього.

Варіант 2: інтегрувати у звичайний Next.js / власний бекенд

Перенести page.tsx, globals.css, layout.tsx, engine.ts, source.json та потрібні компоненти. Замінити Worker/Vite-конфіг на власний збирач. Переписати db/index.ts: імпорт cloudflare:workers не працює у звичайному Node-сервері. Перенести або адаптувати /api/leads, зберігши серверну валідацію та обчислення report. Встановити свій драйвер бази, міграції та авторизацію.

Обидва варіанти — план перенесення, а не вже перевірений зовнішній деплой. Поточний original source залишається точним знімком робочої версії. Не підміняти oai-authenticated-user-id довільним заголовком із браузера на новому хостингу: там його має замінити перевірена серверна сесія.

11. Що підключити для продажів і реклами

CRM. Погодити CRM, URL/метод, права, pipeline, stage, відповідального, правила дублювання номера й маркетингові поля. Рекомендована послідовність: записати заявку → поставити передачу в чергу/outbox → надіслати в CRM → зберегти external ID/статус → повторювати тимчасові помилки без дублювання. Відкриття результату залежить від надійного запису заявки, а не від швидкості зовнішнього CRM API.

Передавати: lead id, телефон, дата, сфера, сам/команда, цілі, контекст, чотири оцінки, пріоритет, висновок, відповіді, версія згоди. В поточній схемі немає readiness, UTM чи variant; не плутати з квізом B. Якщо додаються, потрібні зміни моделі, payload та міграція.

Сповіщення. Узгодити канал менеджерів і SLA першого контакту. Наявний текст про дзвінок не запускає його автоматично. Telegram/email/SMS/календар у поточному коді не підключені.

Аналітика. У A немає вбудованих подій проходження, UTM, GA4/Meta Pixel/CAPI чи A/B-розподілу. Пропоновані події: quiz_view, quiz_start, question_answer, quiz_complete, lead_submit, lead_success. lead_success надсилати після успішного запису, а не по кліку. Додати version, variant=A, session_id, question_index, timestamp, UTM. Не передавати телефон і текстові персональні дані у звичайні аналітичні події. Рекламні інтеграції реалізувати окремо з погодженою моделлю згоди.

A/B. Квіз B — окремий проєкт, у цьому пакеті відсутній. Зберігати позначку варіанта в CRM; порівнювати зіставні аудиторії, періоди, швидкість обробки та цикл продажу. Основний бізнес-показник — вартість покупця; додатково кваліфіковані заявки, зустрічі, конверсія в оплату. Оригінал A не змінювати під час тесту без фіксації нової версії.

12. Дизайн, контент і межі змін

Темний фон, червоні акценти, контрастна типографіка. Кільця з балами, головний висновок і чотири окремі картки рекомендацій — погоджена основа фіналу. Скріншоти з ранніх розмов могли показувати три картки; поточна версія використовує чотири.

Точні відступи, шрифти, кольори, брейкпойнти та стани містяться в globals.css, без необхідності відтворення зі скріншота. Іконки — lucide-react, логотип — текст, кільця — SVG. Немає окремого Figma-макета чи фотобанку в цьому пакеті.

На поточній сторінці залишені затверджені власником дані: 13 років, 100 000+ відвідувань, 10 000+ підприємців і твердження про показники у 2–4 рази. Це перенесений контент, не результат перевірки статистики. Перед новою рекламною кампанією власник має підтвердити актуальні формулювання та підстави для їх використання. Не замінювати 100 000 на інше значення автоматично з інших матеріалів.

Контент редагується в TSX/JSON/engine. CMS немає. Зміна порядку відповідей без одночасної зміни scoring призведе до неправильних результатів. Не переставляти індекси в масивах довільно.

13. Пріоритети підготовки до production

  • Затвердити зовнішній хостинг, доступ відвідувачів та власний захист адмінки. В оригінальній платформі доступ задається окремо від коду.
  • Підключити базу, резервування, серверну валідацію й коректну ідемпотентність; перевірити сценарій повторної заявки після редагування відповідей.
  • Підключити CRM та повідомлення; зробити видимими менеджеру заявки анонімних відвідувачів.
  • Додати захист від масового спаму, обмеження частоти й ліміти на рівні сервера, не покладатися лише на Origin або кнопку disabled.
  • Уточнити політику конфіденційності: відповідальна юридична особа, контакт щодо даних, строки зберігання, видалення, підрядники. Наявне модальне вікно — коротке пояснення, не повний документ для всіх юрисдикцій.
  • Додати UTM/події та зв’язок із покупками, перевірити відсутність персональних даних у логах і пікселях.
  • Якщо потрібна справжня видача прихованого звіту лише після заявки — реалізувати серверний доступ замість CSS-блюру.

Це перелік робіт для перенесення, а не зміни, вже внесені в архів. Доступи до домену/CRM/хостингу передаються власником окремим захищеним способом.

14. Приймальні сценарії

  • Перевірити всі сфери, три варіанти автобізнесу й поле іншої сфери; порожнє уточнення не пропускає далі.
  • Для роботи самостійно — питання про час/домовленості, для команди — найм/введення/делегування.
  • №3 і №20 дозволяють 1–3 відповіді; четвертий вибір не додається; №20 варіант 6 взаємовиключний.
  • Назад/продовжити зберігають стан, зміна сфери/команди очищає відповідні залежні питання.
  • Порожні відповіді не дають завершити тест; усі «не застосовується» не утворюють хибний нульовий рейтинг.
  • Бал 0/50/100 і null відображається правильно; пояснення кільця збігається з реальними відповідями.
  • examples/result-fixtures.json дає тотожні результати після перенесення.
  • До заявки видно передбачену частину; після успішного запису — повні чотири напрями та deepDive.
  • Не можна подати порожній номер або без згоди; помилка сервера залишає відповіді й дозволяє повторити.
  • Повторний клік/таймаут не дублює одну заявку; зміна даних після успіху не губиться під старим id.
  • TXT містить актуальний результат; у файлі немає даних інших людей.
  • Менеджер отримує звернення анонімного відвідувача; сторонній користувач не має доступу до списку лідів.
  • Перевірити 360/390/768/1440 px, довгі тексти, клавіатуру, видимий focus, блокування під час submit, модальні вікна.
  • UTM і variant доходять у CRM, якщо ці інтеграції реалізовані; рекламний lead_success збігається з записом у базі.

15. Інформація від власника перед запуском

Потрібні: цільовий домен і хостинг; назва CRM та її API; поля й відповідальні; канал сповіщень; модель доступу менеджерів; політика даних; аналітичні ідентифікатори; визначення цільового ліда й покупки; актуальні підтверджені маркетингові цифри. Самих секретів та реальних даних відвідувачів у цьому пакеті немає.

Перший результат роботи команди: доступний staging із тотожним квізом, перевіреною базою і тестовою заявкою в обраній CRM. Після приймання — production, перевірка повного шляху заявки й опис процедури відновлення/відкату.
