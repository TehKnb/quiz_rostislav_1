# КНБ — повна інструкція передачі розробникам

**Проєкт:** персональна карта бізнесу, квіз A, 20 запитань. **Дата:** 02.11.2026.

**Еталонний URL:** https://knb-business-growth-quiz.allazovros.chatgpt.site/

**Перевірена версія:** Sites 3, commit `65eb68da197e56a0150ef2f5d547d1552a08cdef`. Локальний commit збігається з джерелом останньої збереженої версії Sites. Вихідне дерево чисте. Оригінал не змінено.

## 1. Завдання продукту

Квіз для власників малого та середнього бізнесу. Він збирає контекст, оцінює чотири напрями процесів і показує персональний висновок. Цільова дія — номер телефону для зв’язку щодо персонального бізнес-розбору КНБ. Після успішної передачі заявки на webhook відкриваються повні пояснення, рекомендації та відеокейси.

Основний офер: «Хочете вдвічі більше чистого прибутку? Що у вашому бізнесі має змінитися першим?» Це бажана ціль відвідувача, не розрахований прогноз зростання. Квіз не обчислює втрачені гроші, не гарантує подвоєння прибутку й не використовує зовнішню ШІ-модель для відповідей.

Результат ґрунтується на детермінованих правилах у `app/lib/engine.ts`. Обов’язково зберегти пояснення про попередній характер рекомендацій і необхідність перевірки показників та внутрішніх процесів на бізнес-розборі.

## 3. Технології й запуск

Стек із поточного package.json: Next.js 16.3.4 (App Router, Node.js), React 19.2.6, TypeScript 5.9.3. База даних не використовується. Production-середовище — Railway.

Вимоги пакета: Node.js 22; менеджер пакетів — pnpm 11.25.0. Команді варто взяти актуальний підтримуваний Node, сумісний із цим lockfile, і спочатку відтворити залежності без їх оновлення. Для встановлення потрібен доступ до npm-реєстру. Не використовуйте автоматичне масове оновлення залежностей до звірки поведінки.

З кореня репозиторію, після встановлення Node і pnpm:

```bash
pnpm install --frozen-lockfile
node tests/engine.cjs
node tests/lead-payload.mjs
pnpm exec tsc --noEmit
pnpm build
```

Для локальної роботи створіть у корені репозиторію файл `.env.local` (ігнорується git, зразок — `.env.example`):

```bash
BUSINESS_REVIEW_WEBHOOK_URL=https://example.com/your-test-webhook
OPENAI_API_KEY=your-test-key
```

`pnpm dev` запускає режим розробки на порту 3000. `pnpm build` і `pnpm start` — production-збірка та сервер на `PORT` (типово 3000), адреса `0.0.0.0`. Без webhook URL форма показує помилку відправки, а результат не відкривається. Без ключа OpenAI власна сфера отримує універсальні запитання.

Замість старих абсолютних шляхів `/workspace/...` і `/root/.codex/...` зі службових описів використовуйте команди вище. Цей архів не включає інструменти публікації ChatGPT. Секретів для логіки квіза не потрібно; для нового production-хостингу знадобляться власні облікові дані хостингу й CRM.

**Перевірка передачі:** 52 базові сценарії, додаткові перевірки мультивибору й звітів за чотирма напрямами пройшли; `tsc --noEmit` завершився успішно. Це перевірка коду в наявному середовищі, не підтвердження чистої інсталяції чи нового зовнішнього деплою.

## 4. Екрани та поведінка

1. **Головна.** Офер, CTA, схема чотирьох напрямів, три короткі кроки пояснення.
2. **Проходження.** Одне запитання за раз, прогрес, назад, збереження/вихід, блокування «Далі» без валідної відповіді. Прогрес показує `step / 20`, де step — індекс від 0.
3. **Результат до заявки.** Сфера, чотири кільцеві оцінки, головний висновок, перший крок, чотири рекомендаційні картки з продовженням під блюром. Натискання оцінки показує питання й відповіді відповідного напряму.
4. **Офер бізнес-розбору.** Дві групи вигод: результат після заявки та персональний розбір. Форма телефону без чекбокса згоди.
5. **Успішна заявка.** Тільки після успіху POST з’являється підтвердження, розгорнуті пояснення, дії, показники, питання на розбір, попередження про попередній характер результатів, кнопка завантаження TXT і слайдер відеокейсів за обраною сферою.
6. **Повторне проходження.** Скидання поточної сесії через підтвердження; раніше надіслані заявки це не скасовує.

Локальний стан: `sessionStorage`, ключ `knb-quiz-v3`. Зберігаються profile, step, view, unlocked, report, receipt. Телефон не зберігається в цьому стані. Продовження працює в тій самій вкладці; це не акаунт і не синхронізація між пристроями. Після закриття вкладки не обіцяти гарантованого відновлення.

## 5. Питання та персоналізація

| № на екрані | Індекс | Призначення |
|---|---|---|
| 1 | 0 | Сфера, додаткове уточнення автобізнесу / іншої діяльності |
| 2 | 1 | Формат роботи / розмір команди |
| 3 | 2 | Цілі; 1–3 відповіді |
| 4–7 | 3–6 | Маркетинг, 4 оцінювані ситуації |
| 8–11 | 7–10 | Продажі, 4 ситуації |
| 12–15 | 11–14 | Команда або особиста організація роботи, 4 ситуації |
| 16–19 | 15–18 | Аналітика, 4 ситуації |
| 20 | 19 | Особисті наслідки / контекст, 1–3 відповіді |

Сфери: медицина, б’юті, одяг/взуття/аксесуари, магазин/інтернет-магазин, автобізнес, харчування, будівництво, виробництво, інша сфера. Автобізнес має `repair`, `cars`, `other`. Для іншої сфери або авто/other потрібен текст мінімум 2 символи після trim; максимум поля — 100 символів. Універсальні запитання використовують ключ `other`.

Варіанти команди 0 та 1 вважаються самостійною роботою; 2, 3, 4 — роботою з командою. Змінюються блок організації роботи, окремі нішеві питання, назви й рекомендації. Точні формулювання є в каталозі; його генеровано викликом `question()` з реального engine, а не написано окремо.

Мультивибір дозволений лише в №3 і №20. Максимум 3; повторне натискання знімає вибір. У №20 варіант з індексом 6 «Нічого з переліченого…» взаємовиключний з іншими. Масиви — `goals` та `impacts`; їх перший елемент дублюється в `answers[2]`/`answers[19]`. Це вимога валідації. Старий формат з одним індексом у answers підтримується fallback-логікою `selected()`.

Зміна вже обраної сфери або формату роботи очищає оцінювані відповіді 3–18. Зміна формату роботи також очищає останнє питання та impacts. Зміна авто-підгілки очищає питання 3–10. Після зміни відповідей повний результат знову закривається.

## 6. Формула балів та головний пріоритет

В оцінюваних питаннях індекс відповіді 0 — найкращий стан, 3 — найслабший. Індекс 4 «Не можу оцінити / не застосовується» виключається з оцінки, не прирівнюється до нуля. Контекстні питання 1–3 та 20 не додають балів.

Для кожної групи потрібні щонайменше 2 відомі відповіді з 4:

`score = Math.round(sum(3 - answerIndex) / (knownCount * 3) * 100)`

Інакше score = null, показуємо тире й недостатність даних. Приклад: відповіді 0, 3, 4, 4 → 50/100; 0, 4, 4, 4 → недостатньо даних. Межі: <40 — потребує уваги; 40–69 — є основа для покращення; >=70 — процеси налагоджені.

Червона дуга кола відображає цей бал зі 100, а не частку пройденого тесту і не відсоток втраченого прибутку. Нуль — лише фон кола; null — тире.

Головний пріоритет — напрям із найменшим доступним балом. За однакових оцінок використовуються обрані цілі, потім особисті наслідки; може повертатися до двох пріоритетів. Точний порядок розв’язання нічиєї — функція `priority()`; для повної тотожності переносити її без спрощення.

Мапа цілей у групи: `[0,1,3,2,2,-1]`. Мапа наслідків: `[0,1,2,2,3,3,-1]`. Групи 0=маркетинг, 1=продажі, 2=організація/команда, 3=аналітика. -1 не задає конкретної групи.

Якщо немає жодної оцінюваної групи — insufficient. Якщо мінімальний пріоритетний бал >=70 — high; висновок пропонує перевірити стійкість процесів до зростання. Важливий нюанс: high стосується лише оцінених напрямів, не означає, що всі чотири мають достатньо даних.

## 7. Побудова персонального результату

`result(profile)` повертає scores, priorities, high, insufficient, evidence, strongSide, conflict, recommendations, directions, deepDive, firstStep, title, explanation, goal, impact, sector.

- `evidence` — до двох найслабших оцінених відповідей головного напряму.
- `directions` — чотири картки: маркетинг, продажі, організація роботи, аналітика. Для кожної — бал, статус, пояснення, до двох предметних кроків, що зафіксувати, як оцінити зміни, що уточнити на розборі. За нестачею даних — заклик зібрати приклади.
- `deepDive` — три частини головного висновку: чому почати тут, зв’язок чотирьох напрямів, послідовність дій.
- `recommendations` — збережене поле з трьома рекомендаціями. Поточний фінальний інтерфейс рендерить саме чотири `directions`; не замінювати їх старим масивом recommendations.
- `strongSide` — одна найсильніша відповідь, переважно з іншого напряму.
- `conflict` — окреме уточнення, коли економіку пропозицій рахують, а загальний прибуток оцінюють приблизно.

Для fashion/shop є окремий висновок про покупки, що губляться в діалогах: він застосовується, коли головний пріоритет — продажі та обидві відповіді на індексах 9 і 10 дорівнюють 2 або 3. Для самостійної роботи застосовуються власні заголовки й поради, а не автоматична рекомендація наймати людей.

**Блюр — оформлення, не захист контенту.** Тексти й алгоритм доступні клієнту; unlocked зберігається у sessionStorage. Якщо бізнесу потрібне реальне обмеження доступу, частину звіту потрібно перенести на сервер і видавати за авторизованою сесією/одноразовим токеном після передачі заявки. У поточному проєкті такого механізму немає.

## 8. API заявки

### POST /api/leads

JSON: `id`, `phone`, `profile`. Готовий валідний приклад — `examples/lead-request.json`; номер синтетичний, не використовувати для реального дзвінка.

Profile містить: answers — рівно 20 цілих індексів; auto — рядок; other — рядок до 100 символів; goals/impacts — необов’язкові масиви для мультивибору.

Перевірка Origin порівнює лише хости (`X-Forwarded-Host` або `Host`), бо за HTTPS-проксі сервер бачить `http://`. Послідовність: перевірка Origin і розміру тіла (16000 символів) → нормалізація номера → перевірка profile → `result(profile)` → `buildLeadPayload()` → POST на `BUSINESS_REVIEW_WEBHOOK_URL` → відповідь клієнту. Постійного сховища немає.

Webhook викликається лише на сервері. Таймаут — 15 секунд. Успіхом вважається лише статус 2xx; редиректи не виконуються й вважаються помилкою. У лог потрапляє тільки статус або тип помилки, без номера, відповідей і URL.

| Код | Поточна поведінка |
|---|---|
| 200 | `{id, report}`, Cache-Control: no-store — webhook підтвердив отримання |
| 400 | Некоректний JSON або невідповідність номера/profile |
| 403 | Переданий Origin не відповідає адресі API |
| 413 | Текст тіла довший за 16000 символів |
| 503 | Webhook не налаштований, повернув помилку або не відповів вчасно; UI пропонує повтор |

Клієнтський `id` передається заголовком `Idempotency-Key`. Сайт не може відсіяти дублікати сам: якщо webhook прийняв заявку, але не встиг відповісти за 15 секунд, повторна спроба надішле її ще раз. Отримувач може відсіювати такі повтори за цим заголовком.

### Персоналізація власної сфери (POST /api/personalize)

Коли відвідувач вписує власну сферу («Інша сфера» або «Автобізнес → Інше»), 9 запитань із нішевими формулюваннями (Q4–Q11 і Q17) переформульовує модель OpenAI. Варіанти відповідей, порядок, логіка переходів і формули не змінюються: відповіді зберігаються індексами.

- **Коли:** запит іде у фоні після Q2, бо формулювання залежить від того, чи працює людина сама. Перехід із Q3 на Q4 чекає на відповідь, кнопка показує «Готуємо запитання…».
- **Вхід:** JSON `niche` (2–100 символів) і `solo`. Заголовок Origin обов’язковий. Номер та інші відповіді в OpenAI не передаються.
- **Перевірка відповіді:** JSON Schema на 9 полів, потім `validCustomTitle()`: довжина, знак питання, переважно кирилиця, без російських літер, посилань і розмітки.
- **Збій:** будь-яка помилка, невалідна відповідь або таймаут 8 с дають 503; клієнт мовчки лишає універсальні запитання на весь проходження. Пізня відповідь не застосовується, тож формулювання не змінюються посеред квіза.
- **Зберігання:** формулювання лежать у `profile.custom` (sessionStorage вкладки) і надходять у `/api/leads`. Сервер перевіряє їх тією самою функцією й підставляє в Q/A та `Ai Text` через `question()`.

Змінні: `OPENAI_API_KEY` (обов’язкова), `OPENAI_MODEL` (типово `gpt-4o-mini`), `OPENAI_BASE_URL` (необов’язкова, для шлюзу або тестового сервера). Без ключа квіз працює на універсальних запитаннях.

### Генерація результату (POST /api/leads)

Заголовки, описи під ними, оцінки, пріоритети й цитати відповідей рахує `result()` у `engine.ts`, як і раніше. Пояснення пише модель: три частини головного висновку, а в кожному напрямі «Чому це важливо», два наступні кроки, «Як оцінити зміни» та «Що уточнити на бізнес-розборі».

- **Коли:** лише після надсилання форми. До цього в розмитих блоках стоїть нейтральний текст-заглушка (`blurredConclusion`, `blurredDirection` у `page.tsx`).
- **Послідовність:** генерація, потім вебхук, потім відповідь клієнту, бо `Ai Text` має містити те саме, що бачить відвідувач. Зазвичай це 3–7 секунд.
- **Запити:** 5 паралельних (висновок і 4 напрями), бо один довгий запит тримав би відвідувача значно довше. Спільний таймаут секції 25 с.
- **Вхід:** сфера, чи працює людина сама, цілі, ситуація, оцінки та відповіді. Номер телефону в OpenAI не передається.
- **Перевірка:** JSON Schema, потім `parseConclusion()` і `parseDirection()`: довжина, переважно кирилиця, без російських літер, посилань, розмітки й емодзі, а для тих, хто працює сам, без згадок про команду. Невалідну відповідь запитує ще раз один раз.
- **Збій:** секція, що не вдалася, лишається з готовим текстом із `engine.ts`, а заявка все одно йде у вебхук. Напрям без достатньо даних і висновок без оцінок модель не отримує.
- **Зберігання:** готовий звіт лежить у sessionStorage вкладки, тому після перезавантаження текст не змінюється.

### Payload webhook

Плоский JSON із рядковими значеннями; приклад — `examples/webhook-payload.json`, окремо текст — `examples/ai-text.txt`.

| Поле | Значення |
|---|---|
| name, nameform, source | Сталі значення форми |
| phone | Лише цифри, наприклад `380671234567` |
| Q1–Q20 | Формулювання з `question(step, profile)` — ті самі, що бачив відвідувач |
| A1–A20 | Тексти обраних варіантів; мультивибір (Q3, Q20) через `; `. A1 містить і уточнення: `Автобізнес — СТО / ремонт`, `Інша сфера: Логістика` |
| Ai Text | Один рядок із блоками, зібраний з того самого `report`, який показується на екрані, разом зі згенерованими поясненнями. Блок «ПРІОРИТЕТНІ РЕКОМЕНДАЦІЇ» на екрані не показується і лишається готовим текстом. Загального балу рушій не рахує, тому його немає |

## 9. Зберігання даних

Бази даних немає. Заявка існує лише під час обробки запиту й передається на webhook; відповіді до відправлення лежать у sessionStorage браузера. За збереження заявок відповідає система-отримувач webhook. Чекбокса згоди у формі немає, згода не збирається й не передається.

## 10. Деплой на Railway

Код працює як звичайний Node.js-застосунок Next.js. Dockerfile не потрібен: Railway збирає проєкт через Railpack.

1. Завантажте проєкт у GitHub. Застосунок лежить у корені репозиторію; файли `.env*` не потрапляють у git, крім `.env.example`.
2. У Railway: New Project → Deploy from GitHub repo → оберіть репозиторій.
3. У Settings сервісу залиште **Root Directory** порожнім: Railpack знаходить `package.json` у корені.
4. У Variables задайте `BUSINESS_REVIEW_WEBHOOK_URL`, `OPENAI_API_KEY` і за потреби `OPENAI_MODEL`. `PORT` Railway задає сам.
5. У Settings вкажіть **Healthcheck Path** `/health`.
6. Build і Start Command не змінюйте: Railpack використовує скрипти `build` і `start` із `package.json`.
7. У Networking натисніть Generate Domain, потім пройдіть квіз і перевірте заявку у вебхуку.

Секрети читаються лише на сервері через `process.env` у момент запиту, тому після зміни змінних достатньо перезапуску. Відкат — через попередній деплой у Railway.

## 11. Що підключити для продажів і реклами

**CRM.** Заявки передаються на webhook із `BUSINESS_REVIEW_WEBHOOK_URL` (розділ 8). Погодити на стороні отримувача pipeline, stage, відповідального й правила дублювання номера. Черги чи outbox на сайті немає: якщо webhook недоступний, відвідувач бачить помилку й може повторити відправку.

В поточному payload немає дати, readiness, UTM чи variant; не плутати з квізом B. Якщо вони потрібні, додайте їх у `buildLeadPayload()`.

**Сповіщення.** Узгодити канал менеджерів і SLA першого контакту. Наявний текст про дзвінок не запускає його автоматично. Telegram/email/SMS/календар у поточному коді не підключені.

**Аналітика.** У A немає вбудованих подій проходження, UTM, GA4/Meta Pixel/CAPI чи A/B-розподілу. Пропоновані події: quiz_view, quiz_start, question_answer, quiz_complete, lead_submit, lead_success. lead_success надсилати після успішного запису, а не по кліку. Додати version, variant=A, session_id, question_index, timestamp, UTM. Не передавати телефон і текстові персональні дані у звичайні аналітичні події. Рекламні інтеграції реалізувати окремо з погодженою моделлю згоди.

**A/B.** Квіз B — окремий проєкт, у цьому пакеті відсутній. Зберігати позначку варіанта в CRM; порівнювати зіставні аудиторії, періоди, швидкість обробки та цикл продажу. Основний бізнес-показник — вартість покупця; додатково кваліфіковані заявки, зустрічі, конверсія в оплату. Оригінал A не змінювати під час тесту без фіксації нової версії.

## 12. Дизайн, контент і межі змін

Темний фон, червоні акценти, контрастна типографіка. Кільця з балами, головний висновок і чотири окремі картки рекомендацій — погоджена основа фіналу. Скріншоти з ранніх розмов могли показувати три картки; поточна версія використовує чотири.

Точні відступи, шрифти, кольори, брейкпойнти та стани містяться в globals.css, без необхідності відтворення зі скріншота. Іконки — lucide-react, логотип — текст, кільця — SVG. Немає окремого Figma-макета чи фотобанку в цьому пакеті.

На поточній сторінці залишені затверджені власником дані: 13 років, 100 000+ відвідувань, 10 000+ підприємців і твердження про показники у 2–4 рази. Це перенесений контент, не результат перевірки статистики. Перед новою рекламною кампанією власник має підтвердити актуальні формулювання та підстави для їх використання. Не замінювати 100 000 на інше значення автоматично з інших матеріалів.

Контент редагується в TSX/JSON/engine. CMS немає. Зміна порядку відповідей без одночасної зміни scoring призведе до неправильних результатів. Не переставляти індекси в масивах довільно.

## 13. Пріоритети підготовки до production

1. Налаштувати домен і змінні на Railway.
2. Налаштувати `BUSINESS_REVIEW_WEBHOOK_URL` і дедуплікацію на стороні отримувача; перевірити сценарій повторної заявки після редагування відповідей.
3. Перевірити, що заявки з webhook доходять до менеджера.
4. Додати захист від масового спаму, обмеження частоти й ліміти на рівні сервера (особливо для `/api/personalize` і `/api/leads`, бо кожен виклик витрачає бюджет OpenAI), задати ліміт витрат у проєкті OpenAI, не покладатися лише на Origin або кнопку disabled.
5. Уточнити політику конфіденційності: відповідальна юридична особа, контакт щодо даних, строки зберігання, видалення, підрядники. Наявне модальне вікно — коротке пояснення, не повний документ для всіх юрисдикцій.
6. Додати UTM/події та зв’язок із покупками, перевірити відсутність персональних даних у логах і пікселях.
7. Якщо потрібна справжня видача прихованого звіту лише після заявки — реалізувати серверний доступ замість CSS-блюру.

Це перелік робіт для перенесення, а не зміни, вже внесені в архів. Доступи до домену/CRM/хостингу передаються власником окремим захищеним способом.

## 14. Приймальні сценарії

- Перевірити всі сфери, три варіанти автобізнесу й поле іншої сфери; порожнє уточнення не пропускає далі.
- Для роботи самостійно — питання про час/домовленості, для команди — найм/введення/делегування.
- №3 і №20 дозволяють 1–3 відповіді; четвертий вибір не додається; №20 варіант 6 взаємовиключний.
- Назад/продовжити зберігають стан, зміна сфери/команди очищає відповідні залежні питання.
- Порожні відповіді не дають завершити тест; усі «не застосовується» не утворюють хибний нульовий рейтинг.
- Бал 0/50/100 і null відображається правильно; пояснення кільця збігається з реальними відповідями.
- `examples/result-fixtures.json` дає тотожні результати після перенесення.
- До заявки видно передбачену частину; після успішної відповіді webhook — повні чотири напрями, deepDive, попередження та відеокейси.
- Не можна подати порожній або некоректний номер; помилка сервера залишає відповіді й дозволяє повторити.
- Повторний клік не дублює заявку; після таймауту відвідувач може повторити відправку (можливий дублікат з тим самим `Idempotency-Key`); зміна даних після успіху отримує новий id.
- TXT містить актуальний результат; у файлі немає даних інших людей.
- Менеджер отримує звернення анонімного відвідувача; сторонній користувач не має доступу до списку лідів.
- Перевірити 360/390/768/1440 px, довгі тексти, клавіатуру, видимий focus, блокування під час submit, модальні вікна.
- UTM і variant доходять у CRM, якщо ці інтеграції реалізовані; рекламний lead_success збігається із заявкою на webhook.

## 15. Інформація від власника перед запуском

Потрібні: цільовий домен і хостинг; назва CRM та її API; поля й відповідальні; канал сповіщень; модель доступу менеджерів; політика даних; аналітичні ідентифікатори; визначення цільового ліда й покупки; актуальні підтверджені маркетингові цифри. Самих секретів та реальних даних відвідувачів у цьому пакеті немає.

Перший результат роботи команди: доступний staging із тотожним квізом і тестовою заявкою, що дійшла через webhook до обраної CRM. Після приймання — production, перевірка повного шляху заявки й опис процедури відновлення/відкату.
